- (decision by user) CI reaches the VM only through Tailscale: ephemeral node from an OAuth client tagged tag:ci; ACL allows tag:ci -> tag:server:22 only; OCI security list opens only 80/443. Prevents a public SSH port and long-lived CI auth keys. Rationale: security teams require closed port 22; GitHub IP ranges too wide to allowlist; self-hosted runners unsafe on public repos
- (decision by user) OpenSSH bound to tailscale0, dedicated deploy user, one SSH key per environment in GitHub Environment secrets, authorized_keys forced command deploy.sh <env> <digest>. Prevents a leaked CI key from getting a shell (docker group = root). Chosen over Tailscale SSH because forced command limits what a key can do
- (decision by user) Secrets live in GitHub Environments; deploy passes them over SSH stdin, deploy.sh writes the compose project .env with mode 600; never in argv or logs
- (decision by user) Break-glass access via OCI serial console connection, tested once and written in a runbook. Server Tailscale auth key is one-off, pre-authorized, short-lived because it lands in user_data and Terraform state
- (decision by user) Image identity = git tree hash (git rev-parse HEAD^{tree}); extra tag sha-<commit> and OCI label org.opencontainers.image.revision. Rationale: a GitHub merge commit has a new sha but the same tree as main when branches did not diverge; HEAD^2 silently deploys wrong code if rc diverged
- (decision by user) Each tree is built at most once: any env pipeline resolves the tree tag, reuses the image if present, otherwise builds, scans with Trivy and pushes to GHCR. Replaces README line 'built once per commit on main'
- (decision by user) Deploy by digest: tag resolved once to image@sha256, digest passed to deploy.sh, written to job summary and env .env; rollback = previous digest stored on the VM. Prevents mutable GHCR tags from changing what runs
- (decision by user) Branch flow: rc accepts PRs from main or hotfix/*, prod only from rc, enforced by a required status check; rc and prod allow merge commits only (rulesets). Hotfix: hotfix/* -> rc -> prod, then cherry-pick into main. Required check on main->rc PRs: merge tree must equal main's tree, else fail listing files missing in main
- (decision) Promotion job checks the image exists (docker buildx imagetools inspect) and fails with a clear message instead of waiting, covering the race with a main build still running
- (decision by user) Deploy sequence: record alembic current; alembic upgrade head; start new digest; gate on /health; on failure run alembic downgrade <recorded> with the NEW image (old image lacks the new migration files), then start previous digest. A failed migration rolls back in its own transaction and leaves the old container untouched
- (decision by user) Every migration has a working downgrade, tested in CI: upgrade head -> downgrade base -> upgrade head on an empty database
- (decision by user) Convention instead of pre-deploy pg_dump: a migration never deletes or moves data in the same release as the code change. Rationale: rollback happens within the deploy health gate so added columns stay empty; only destructive upgrades lose data
- (assumption) With plain docker compose up, the new container receives traffic before the health verdict; requests in that window may write to new columns. Accepted for a demo without real load; blue-green deferred
- (decision by user) One PostgreSQL and one Redis container per environment compose project; same compose file for all envs, difference only in .env. Prevents a dev deploy or Postgres upgrade from touching prod. Rejected: shared cluster in platform stack (couples app to platform)
- (decision) mem_limit on every container; Postgres shared_buffers ~128MB. Prevents one env's leak from OOM-killing prod on a 12 GB VM
- (decision) One postgres_exporter in the platform stack in multi-target mode; Prometheus adds the env label
- (decision by user) Minimal Terraform moves to the start of Phase 3: VCN, subnet, security list (80/443), VM, separate data block volume with prevent_destroy. State bucket created once by hand (bootstrap). Recreate server: terraform apply -replace on the instance. Rejected: manual VM then terraform import (busywork, weaker IaC story)
- (decision by user) cloud-init owns only the base OS and runs once: Docker, Tailscale, deploy user with forced command, sshd on tailscale0, data volume mounted for Docker volumes. Base OS change = VM replacement (immutable server). Platform stack deployed by its own workflow on changes under deploy/platform/. Ownership: Terraform = machine, cloud-init = OS, pipelines = stacks
- (decision) Caddy reaches app stacks through a shared external docker network edge joined only by each env's API container; databases and Redis stay on the env's private network
- (decision) DuckDNS: one name, environments on sub-subdomains (dev.<name>.duckdns.org) which DuckDNS resolves to the same IP; the 5-subdomain limit does not bind
- (decision by user) n8n is shared by three envs, parameterised per env (credentials of a demo staff account, internal API URL over edge network, not the public domain). n8n runs the kitchen simulator: cron every 5-10 minutes advances orders through the API, no LLM. n8n is on the prod critical path
