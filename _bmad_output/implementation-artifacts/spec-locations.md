## Intent

**Problem:** The Figma main page "Locations" cards (photo, address, "N tables") and the "Restaurant Profile" page (node 111691:73904: photo, address, "Atmosphere" description) have no backend, so the frontend cannot finish them.

**Approach:** A core feature `features/core/locations` with two public read routes, `GET /api/v1/locations` and `GET /api/v1/locations/{id}`. Locations and their dining tables are reference data inserted by migrations; photos live in the media bucket like dish pictures. First, the menu moves to `features/core/menu`, because later features (cart, orders) build on it.

## Boundaries & Constraints

**Always:**
- Decision (Vlad, 2026-11-10): menu and locations are core features, shared like users; cart and later features are regular. The menu move is a pure move in its own commit before the locations commit: same behaviour, routes, tests and migrations, only import paths change.
- Decision (Vlad): tables are rows, not a count column; "N tables" is the number of a location's tables, computed by the query. Tables seat 2 to 8.
- Decision (Vlad): locations, tables and menu are reference data shipped by migrations to all environments; ids are generated by each database.
- Decision (Vlad): business rules live in services; database constraints are only a backstop.
- `locations`: `id` (uuid, `gen_random_uuid()`), `slug` (`String(100)`, unique), `address` (`String(200)`), `description` (`Text`), `image_key` (`String(300)`), `created_at`, `updated_at`. `dining_tables`, no timestamps: `id` (uuid, `gen_random_uuid()`), `location_id` (FK, `ON DELETE CASCADE`), `label` (`String(50)`), `capacity` (int), unique `uq_dining_tables_location_id_label`, CHECK named `capacity_between_2_and_8`; no separate index on `location_id`.
- Decision (Vlad): two revisions. `0008` creates `locations` and inserts the three rows with fixed timestamps from 2026-11-10 12:00 UTC, the first location earliest and each next one minute later. `0009` creates `dining_tables` and inserts the tables with `insert().from_select(...)`, finding each location by slug, `id` left to the server default. Capacities expand in the listed order, so `Table 1` is the first two-seater and `Table N` the last eight-seater:
  - `48-rustaveli-avenue`, "48 Rustaveli Avenue": 10 tables, 3 × 2, 4 × 4, 2 × 6, 1 × 8 seats
  - `14-baratashvili-street`, "14 Baratashvili Street": 16 tables, 4 × 2, 7 × 4, 3 × 6, 2 × 8
  - `9-abashidze-street`, "9 Abashidze Street": 20 tables, 5 × 2, 9 × 4, 4 × 6, 2 × 8
- Descriptions (Vlad: the first from Figma, the other two written in its style):
  - Rustaveli: "Located on bustling Rustaveli Avenue, this branch offers a perfect mix of city energy and a cozy atmosphere. With its spacious outdoor terrace, this location is ideal for both casual lunches and intimate dinners."
  - Baratashvili: "Set on a quiet street at the edge of the old town, this branch pairs warm wooden interiors with a calm, green courtyard. Its long shared tables make it a favourite for family dinners and gatherings with friends."
  - Abashidze: "In the leafy Vake district, this bright, plant-filled branch has a relaxed neighbourhood feel. Large windows and an open kitchen make it ideal for slow brunches and easy evenings."
- `image_key` is `locations/<slug>.jpg`; responses carry `image_url` = `MEDIA_PUBLIC_BASE_URL` + `/` + key, built by the service as in the menu.
- List: every location, no pagination, ordered by `created_at ASC, id ASC`; an item is `id`, `address`, `image_url`, `table_count` (outer join, `count(dining_tables.id)`). Item route adds `description`; unknown id → 404 `LOCATION_NOT_FOUND`.
- Both routes are public under one OpenAPI tag "Locations", placed between "Menu" and "Health".
- Decision (Vlad): photos are uploaded as last time, from the developer machine with the local `MEDIA_*` keys, after the local database is at head: `uv run python -m app.scripts.seed_location_photos <dir>`. `LocationPhotoSeedService` (session and `S3FileStorage` injected) reads every location from the database and requires `<dir>/<slug>.jpg` for each; otherwise it raises `LocationPhotoSeedError` (`LOCATION_PHOTOS_MISSING`, listing the slugs) before any upload. Then it puts each file under the location's `image_key` with `image/jpeg`. The script only builds settings, session and storage and runs it, as `seed_menu` does; it writes nothing to the database. No generic uploader.

**Never:** rating, daily occupancy or any invented metric; reviews, booking, slots, opening hours, carts, orders; a route listing tables; writes through the API; a script that writes locations to the database; behaviour changes in the menu.

## Design Notes

- The table is `dining_tables` and the model `DiningTable`: `TABLES` is a PostgreSQL keyword and `Table` collides with SQLAlchemy's `Table`.
- No code path writes tables in this story, so the 2–8 rule exists only as the CHECK backstop for now; the service-level check comes with the first write path.
- Staging and prod need the photos in their own buckets (`backend-showcase-media-<env>`) before they serve working `image_url`s.
