- (direction) Vlad asked to describe the whole initiative as stories, not separate specs. One umbrella spec with stories.yaml; supersedes spec-booking-simulation-patterns (its decisions are carried over here).
- (decision) Carried over: no history backfill, dev only (staging and prod on paper), bot password unchanged, bots via public dev API, 4-free-tables rule, weights in one config object, workflow in git, run every 2 minutes (assumption).
- (capability) CAP-1 a guest can request a booking for 5 to 8 people; the request does not hold the table and several requests may compete for one table and time.
- (capability) CAP-2 a staff member lists pending requests and approves or rejects them; approving one rejects the overlapping pending requests; approval fails if the table was taken meanwhile.
- (capability) CAP-3 participants learn the decision through an in-app notification and an email; no email to example.com addresses.
- (capability) CAP-4 a request with no decision 2 hours before its start is rejected automatically.
- (capability) CAP-5 bot bookings follow time, day and holiday patterns.
- (capability) CAP-6 about 40 bot guests with personas and one staff bot exist on dev.
- (capability) CAP-7 bots pre-order dishes after booking.
- (capability) CAP-8 bots cancel a share of bookings.
- (capability) CAP-9 bots send large-party requests on weekends and holidays.
- (capability) CAP-10 a waiter bot in n8n decides on pending requests with a realistic delay, approving most.
- (capability) CAP-11 Grafana is public with anonymous Viewer and reads dev data through a role that sees no personal data.
- (capability) CAP-12 dashboards for bookings, dishes, checks, visitors and staff work.
